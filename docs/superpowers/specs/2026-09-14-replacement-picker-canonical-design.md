# Екран вибору зміни для підміни — перехід на канонічне джерело

**Date:** 2026-09-14
**Status:** Draft (design); implementation not started.

## Problem

Екран «🔁 Шукати підміну» читає локальне дзеркало `WorkShift`, тоді як екран
«🗓 Мій графік» читає канонічний бекенд напряму. Джерела різні, тож екрани
розходяться: у вікні між правкою графіка і найближчим циклом синку (5 хв)
зміна вже видима в графіку, але ще не доступна для пошуку підміни.

Підтверджено логами проду (14.09.2026, за 3 доби):

| Подія | Значення |
|---|---|
| `shift_not_mirrored`, `skipped:1` | 31 раз |
| `shift_not_mirrored`, `projectedCount:0` | 6 разів — людина не побачила жодної зміни |
| `bot.aws_business_snapshot.synced` | 15 успішних циклів |
| `bot.schedule_mirror.stale` | 0 — синк здоровий |
| `SHIFT_NOT_MAPPED` | 0 — маппінг змін повний |

Тобто це не аварія синку, а структурна властивість: доки екран читає дзеркало,
затримка існуватиме завжди.

Окремо: `ReplacementRequest.workShiftId` прив'язує заявку до локального рядка,
тому дзеркало не можна прибрати, не перенісши цей зв'язок.

## Goal

Привести екран вибору до того ж джерела, що й графік, і зняти залежність
заявки від локального `WorkShift.id`.

**Hard constraint:** живі заявки (ACTIVE / FOUND) з відкритими оферами в
Telegram не повинні осиротіти на жодному кроці.

## Key Decisions

1. **Без прапорця.** Рішення користувача: перехід виїжджає одразу, без
   `*_ENABLED`-перемикача. Відкат — через revert PR, не через конфіг.
2. **Канон — джерело списку; дзеркало — лише фільтр «вже є заявка».** Заявки
   живуть локально, тож фільтр за ними лишається локальним запитом.
3. **Жодних синтетичних id.** Проєктор уже попереджає: вигаданий id ламає
   дедуплікацію нагадувань у Redis (`shift-reminder:<дата>:<staff>:<shift.id>`).
4. **Expand/contract для зв'язку**, а не одномоментна міграція — через живі
   офери.
5. **Фоллбек на дзеркало** при недоступності канону: екран не має падати через
   мережу. Ідіома вже є в `staff-schedule-view.ts`.
6. Тексти для фотографині — українською (AGENTS.md).

## Architecture

### Етап 1 — екран читає канон

```
було:  listSelectableShifts → prisma.workShift (дзеркало)
стане: listSelectableShifts → employeeSchedule (канон)
                            → projectCanonicalSchedule (локальний id для кнопки)
                            → фільтр активних заявок (локально)
```

Вікно запиту — ті самі 62 дні (`SELECTABLE_HORIZON_DAYS`), що вже узгоджені з
`MAX_LIST_DAYS` бекенду.

Проєкція потрібна, бо кнопка й `showReplacementConfirmation` оперують
`WorkShift.id`. Зміна, якої ще немає в дзеркалі, локального id не дасть і на
етапі 1 пропускається — рівно як зараз у графіку. Етап 2 знімає це остаточно.

### Етап 2 — зв'язок на канонічний id

Три кроки, кожен окремим PR, система робоча після кожного:

**2.1 Expand.** Додати `ReplacementRequest.scheduledShiftPublicId String?`.
Писати обидва поля. Читати поки що старе.

**2.2 Backfill.** Заповнити нове поле для наявних заявок через
`WorkShift.awsScheduledShiftPublicId` (вже `@unique`). Перемкнути читання на
нове поле, зберігши старе як запасне для рядків, де бекфіл не спрацював.

**2.3 Contract.** Коли живих заявок зі старим полем не лишиться — зняти
`workShiftId` і зв'язок `workShift`. Не раніше.

«Жива» тут означає статус `ACTIVE` або `FOUND`: саме вони мають відкриті офери
в Telegram і ще змінюються. `CANCELLED`, `EXPIRED`, `FAILED` і
`CLOSED_BY_SCHEDULE_SYNC` — історія, вона переживе зняття поля.

Після 2.3 етап-1 фоллбек на дзеркало для списку більше не потрібен:
кнопка може нести канонічний id напряму.

## Data Flow

Етап 1, звичайний шлях:

1. Фотографиня тисне «Шукати підміну»
2. `employeeSchedule(employeePublicId, from, to)` — 62 дні
3. `projectCanonicalSchedule` дає локальні id
4. Локальний запит відкидає зміни з активною заявкою
5. `buildShiftPickerView` вирішує, що показати і що сказати

Канон недоступний:

1. Крок 2 кидає помилку
2. Лог `bot.replacement_picker_canonical_read.fallback` з `reasonCode`
3. Читання з дзеркала — поточна поведінка
4. Людина бачить список; про фоллбек їй не повідомляють (дані валідні, просто
   можливо на 5 хв старіші)

## Error Handling

| Випадок | Поведінка |
|---|---|
| Канон недоступний / таймаут | Фоллбек на дзеркало + `warn` у лог |
| Співробітниця без `awsEmployeePublicId` | Фоллбек на дзеркало (`EMPLOYEE_NOT_MAPPED`) |
| Локація не змаплена | Як у графіку: `LOCATION_NOT_MAPPED` → фоллбек |
| Зміна є в каноні, немає в дзеркалі (етап 1) | Пропуск + наявний `shift_not_mirrored` |
| Бекфіл не знайшов відповідність (2.2) | Рядок лишається на старому полі; читання має запасний шлях |

Таймаут читання — `USER_VISIBLE_READ_TIMEOUT_MS` (3 с), як у графіку: екран
перед людиною не має висіти довше.

## Testing

Етап 1:
- список будується з канону, а не з дзеркала
- зміна з активною заявкою відфільтрована
- канон недоступний → фоллбек на дзеркало, лог із `reasonCode`
- зміна без дзеркала пропускається, решта показується
- горизонт 62 дні зберігається

Етап 2:
- 2.1: створення заявки пише обидва поля
- 2.2: бекфіл заповнює наявні рядки; читання віддає перевагу новому полю
- 2.2: рядок без відповідності лишається читабельним через старе поле
- 2.3: заявок у статусі ACTIVE/FOUND зі старим полем немає (запит-передумова в PR)

Регресія: повний прогон (нині 1041 файл / 6857 тестів) на кожному PR.

## Rollout

| PR | Зміст | Ризик |
|---|---|---|
| 1 | Етап 1: екран на канон + фоллбек | Низький — схема не змінюється |
| 2 | 2.1 expand: нове поле, подвійний запис | Низький — адитивна міграція |
| 3 | 2.2 backfill + перемикання читання | Середній — торкається наявних заявок |
| 4 | 2.3 contract: зняти `workShiftId` | Середній — незворотний |

Між PR 3 і PR 4 — пауза, доки не закриються заявки, створені до переходу.

## Out of Scope

- Шість читачів групи A (логістика, вікторина, gap-аналіз) —
  `canonical-schedule-remaining-readers.md` обґрунтовує, чому їх не переводять.
- `WorkShift` як таблиця: після 2.3 вона лишається, бо її наповнює синк і
  читають інші місця. Йдеться лише про зв'язок заявки.

## Прийняте відхилення від документа проєкту

`canonical-schedule-remaining-readers.md` відносить `replacement-service.ts:103`
до групи B — «не переводити», бо це запит за локальним `id`.

Аргумент документа стосується фонових читачів: там мережевий збій
перетворюється на втрачену дію, а свіжість у 5 хвилин нічого не змінює. Для
цього екрана баланс інший — перед ним стоїть людина і чекає, тож свіжість
важливіша; фоллбек на дзеркало зберігає стійкість до збою.

Після впровадження цей розділ документа слід оновити, щоб наступний читач не
вважав розходження недоглядом.
